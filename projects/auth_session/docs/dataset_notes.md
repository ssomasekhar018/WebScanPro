# Dataset Notes: Authentication & Session Security

## Overview

This document describes the authentication and session security dataset, including data collection methodology, labeling heuristics, privacy sanitization procedures, and validation statistics.

**Dataset Files:**
- `login_session_dataset.csv` - Raw event-level dataset with labels
- `feature_dataset.csv` - ML-ready features extracted from raw events
- `raw_login_events_<timestamp>.log` - Raw JSON logs for audit trail

---

## Data Collection Methodology

### Collection Environment

The dataset is generated by simulating authentication events against a controlled test environment (dev/staging). The scanner (`auth_scanner.py`) replays attack patterns defined in `attack_patterns.csv` and normal user flows.

### Event Capture

Each authentication event captures the following information:

1. **Event Metadata**
   - `event_id`: Unique UUID for each event
   - `timestamp`: ISO8601 UTC timestamp

2. **User Identity** (anonymized)
   - `username_anon`: HMAC-SHA256 hash of username (preserves grouping)
   - `user_id`: Tokenized user identifier if available

3. **Network Information** (anonymized)
   - `ip_address_anon`: HMAC-SHA256 hash of IP address
   - `geolocation`: Country/region (optional, not included in current dataset)

4. **Request Details**
   - `endpoint`: Authentication endpoint (e.g., `/login`, `/logout`, `/session/refresh`)
   - `method`: HTTP method (POST, GET)
   - `user_agent`: Browser/user agent string

5. **Response Information**
   - `status_code`: HTTP status code (200, 401, 423, 429, etc.)
   - `auth_result`: Authentication result (`success`, `failure`, `locked`, `rate_limited`)
   - `failure_reason`: Specific failure reason (`bad_password`, `invalid_user`, `locked`, `rate_limited`, `unknown`)

6. **Rolling Window Counters**
   - `attempt_count_for_username`: Login attempts for username in last 10 minutes
   - `attempt_count_from_ip`: Login attempts from IP in last 10 minutes
   - `time_since_last_attempt_for_username`: Seconds since last attempt for username

7. **Session Information**
   - `session_id`: Anonymized session token identifier
   - `session_duration`: Session lifetime in seconds
   - `session_reused_flag`: Binary flag indicating session token reused from different IP

8. **Labels**
   - `is_bruteforce_candidate`: Heuristic label for brute-force patterns (0/1)
   - `is_anomalous`: Final ML label for suspicious/malicious behavior (0/1)
   - `password_correct_flag`: Binary flag indicating correct password used (test harness only)

## Labeling Heuristics

### Automated Labeling Rules

#### is_bruteforce_candidate = 1

An event is labeled as a brute-force candidate if **any** of the following conditions are met:

1. **High-frequency single-account attacks**
   - `attempt_count_for_username >= 10` within 10 minutes
   - Indicates repeated attempts against same account

2. **Distributed credential stuffing**
   - `attempt_count_from_ip >= 50` across multiple usernames within 10 minutes
   - Single IP attempting many different accounts

3. **Multi-IP credential stuffing**
   - More than 5 distinct IPs attempting the same username within 1 hour
   - Distributed attack pattern

**Rationale**: These patterns are characteristic of automated brute-force or credential stuffing attacks, distinguishing them from normal user errors (1-3 wrong attempts before success).

#### is_anomalous = 1

An event is labeled as anomalous if **any** of the following conditions are met:

1. **Geographic anomaly** (if geolocation data available)
   - Successful login from different country < 1 minute after last login from another country
   - Indicates potential account takeover or session hijack

2. **Session reuse anomaly**
   - `session_reused_flag = 1`: Same session token used from different IP within 5 minutes
   - Violates normal session behavior

3. **Rate limiting triggered**
   - `status_code == 429` (Too Many Requests)
   - System detected and rate-limited suspicious activity

4. **Brute-force candidate**
   - `is_bruteforce_candidate = 1`
   - All brute-force patterns are considered anomalous

5. **Suspicious success pattern**
   - Successful login (`auth_result == 'success'`) after `>= 5` failed attempts for same username
   - Indicates account compromise after reconnaissance

**Rationale**: These patterns indicate malicious behavior beyond simple brute-force: account takeover, session hijacking, or sophisticated attack patterns.

### Manual Review Flags

The following patterns are flagged for manual review (not automatically labeled):

1. **Borderline geolocation changes**
   - Same region but different city (may be legitimate travel)
   - Requires context to determine legitimacy

2. **Low-attempt anomalies**
   - 5-9 attempts for username (below brute-force threshold but suspicious)
   - May indicate targeted reconnaissance

3. **Legitimate but unusual patterns**
   - VPN usage (appears as distributed but may be legitimate)
   - Corporate networks with multiple IPs
   - Requires domain knowledge to classify

### Label Validation Statistics

After automated labeling, the dataset typically contains:

- **Normal events**: 70-80% (`is_anomalous = 0`)
- **Anomalous events**: 20-30% (`is_anomalous = 1`)
- **Brute-force candidates**: ~15-25% of total events

**Note**: These percentages depend on attack pattern mix in `attack_patterns.csv`. Adjust pattern selection to balance dataset for training.

## Privacy Sanitization

### Anonymization Method

All personally identifiable information (PII) is anonymized using **HMAC-SHA256** with a salted key to preserve grouping while protecting privacy.

#### Username Anonymization

```python
username_anon = HMAC-SHA256(salt, username)[:16]
```

- Preserves grouping: Same username always produces same hash
- One-way: Original username cannot be recovered
- Collision-resistant: Different usernames produce different hashes with high probability

#### IP Address Anonymization

```python
ip_address_anon = HMAC-SHA256(salt, ip_address)[:16]
```

- Preserves grouping: Same IP produces same hash
- Enables IP-based feature aggregation
- Original IP cannot be recovered

#### Session ID Anonymization

```python
session_id_anon = HMAC-SHA256(salt, session_id)[:16]
```

- Preserves session tracking: Same session token produces same hash
- Enables session-based feature extraction
- Original session tokens cannot be recovered

### Salt Management

- **Development/Testing**: Default salt embedded in code (`auth_dataset_salt_2025`)
- **Production**: Salt should be:
  - Generated using secure random (e.g., `secrets.token_hex(32)`)
  - Stored in environment variable or secure config
  - Never committed to version control
  - Rotated periodically for enhanced security

### Data Removal

The following sensitive data is **never** stored in the dataset:

1. **Plaintext credentials**
   - Passwords are never logged (only `password_correct_flag` binary indicator)
   - Usernames are hashed before storage

2. **Full session tokens**
   - Only anonymized session identifiers stored
   - Original tokens cannot be recovered

3. **Original IP addresses**
   - Only hashed IP addresses stored
   - Geolocation data (if collected) should be aggregated (country-level, not city)

4. **User identifiers**
   - All user identifiers are tokenized/hashed
   - No email addresses, real names, or other PII

### Compliance Considerations

- **GDPR**: Anonymized data with irreversible hashing
- **CCPA**: No personal information stored
- **HIPAA** (if applicable): All identifiers tokenized

**Recommendation**: Review dataset with privacy/legal team before production use.

## Feature Extraction

### Feature Categories

The `feature_dataset.csv` contains ML-ready features extracted from raw events:

#### 1. Username-Level Features (Rolling Windows)

- `fail_count_5m`: Failed login attempts in last 5 minutes
- `fail_count_15m`: Failed login attempts in last 15 minutes
- `fail_count_60m`: Failed login attempts in last 60 minutes
- `succ_count_60m`: Successful logins in last 60 minutes
- `fail_success_ratio`: Ratio of failures to successes (60m window)
- `distinct_ips_60m`: Number of distinct IPs attempting username (60m)
- `distinct_user_agents_60m`: Number of distinct user agents (60m)
- `avg_time_between_attempts`: Average seconds between attempts
- `entropy_of_username`: Shannon entropy of username (detects automated usernames)

#### 2. IP-Level Features

- `attempts_per_minute`: Average login attempts per minute from IP
- `distinct_usernames_attempted`: Number of distinct usernames attempted from IP
- `suspicious_ip_flag`: Binary flag for known proxy/TOR IPs (placeholder)

#### 3. Session-Level Features

- `session_duration_seconds`: Lifetime of session in seconds
- `actions_after_login_count`: Number of non-login actions after successful login
- `session_ip_variation_flag`: Binary flag indicating session used from multiple IPs

#### 4. Temporal Features

- `login_hour_local`: Hour of day (0-23)
- `weekday`: Day of week (0=Monday, 6=Sunday)

#### 5. Engineered Features

- `velocity_score`: Composite score combining attempt frequency and IP changes (0-1)
- `geolocation_change_flag`: Binary flag for rapid geolocation changes (placeholder)

### Feature Extraction Methodology

1. **Rolling Windows**: Features computed using time-based sliding windows (5m, 15m, 60m)
2. **Aggregation**: Per-username, per-IP, per-session aggregations
3. **Deterministic**: Same input always produces same features (important for training/eval split)
4. **Preserved Grouping**: Anonymized identifiers preserve grouping across train/test sets

### Feature Validation

- **Missing Values**: Handled with defaults (0 for counts, empty strings for IDs)
- **Outliers**: Velocity scores capped at 1.0 (normalized)
- **Temporal Consistency**: Features computed relative to event timestamp (no future data leakage)

## Dataset Validation Statistics

### Expected Dataset Size

- **Small test run**: 100-500 events
- **Standard run**: 1,000-5,000 events
- **Full dataset**: 10,000+ events (recommended for ML training)

### Data Quality Checks

Run these checks after dataset generation:

1. **Label Distribution**
   - `is_anomalous`: Should have 20-30% positive class
   - `is_bruteforce_candidate`: Should have 15-25% positive class

2. **Missing Values**
   - Check for NULL/empty values in critical fields
   - Validate anonymization (no plaintext usernames/IPs)

3. **Temporal Consistency**
   - Timestamps should be in chronological order (within tolerance for parallel requests)
   - No future timestamps

4. **Session Integrity**
   - Session IDs should be consistent (same session = same hash)
   - Session reuse flags should align with IP changes

5. **Feature Ranges**
   - Count features: Non-negative integers
   - Ratios: Non-negative floats
   - Flags: Binary (0/1)

### Validation Script

```bash
# Run feature extraction
python projects/auth_session/ml/feature_extractor.py --input login_session_dataset.csv --output feature_dataset.csv

# Validate dataset (example checks)
python -c "
import pandas as pd

print(f'Total events: {len(df)}')
```

## Usage Guidelines

### Training ML Models

1. **Split Dataset**: Use temporal split (80% train, 20% test) to avoid data leakage
2. **Feature Selection**: Start with username-level and IP-level features
3. **Class Balancing**: Use SMOTE or class weights if label imbalance is severe
4. **Cross-Validation**: Use time-series cross-validation (not random shuffle)

### Model Evaluation

- **Metrics**: Precision, Recall, F1-score, AUC-ROC
- **Focus**: High recall for anomaly detection (minimize false negatives)
- **Threshold Tuning**: Adjust decision threshold based on operational requirements

### Production Deployment

1. **Feature Pipeline**: Replicate feature extraction logic in production
2. **Real-time Scoring**: Extract features for incoming events, score with trained model
3. **Monitoring**: Track prediction distribution, drift detection
4. **Feedback Loop**: Collect false positives/negatives for model retraining
