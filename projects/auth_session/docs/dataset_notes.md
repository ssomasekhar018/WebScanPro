# Dataset Notes: Authentication & Session Events

This document provides context and rules regarding the `login_session_dataset.csv` and `feature_dataset.csv` files.

## 1. Data Sanitization and Anonymization

To protect user privacy and secure sensitive information, the following sanitization rules are applied to the raw data before it is stored in `login_session_dataset.csv`.

- **IP Address (`ip_address`)**
  - **Method**: Hashed using a non-reversible algorithm (SHA-256) with a salt.
  - **Reason**: Prevents direct identification of the source IP while still allowing for the tracking of activity from a specific source.

- **Username (`username`)**
  - **Method**: Tokenized or replaced with a pseudonym (e.g., `user_1`, `user_2`). A mapping is kept in a secure, separate location only for the duration of the test if needed for debugging.
  - **Reason**: Protects the identity of the user accounts.

- **User ID (`user_id`)**
  - **Method**: Anonymized or hashed, similar to the username.
  - **Reason**: Prevents linking activity to a specific internal user identifier.

- **Session ID (`session_id`)**
  - **Method**: Hashed or tokenized.
  - **Reason**: Protects the actual session token from being exposed in the dataset.

- **Credentials and Tokens**
  - **Method**: Passwords, API keys, and other authentication tokens are **never** logged or stored in the dataset. The `password_correct_flag` is a boolean generated by the test harness and does not expose the actual password.
  - **Reason**: Critical security measure to prevent credential leakage.

- **Timestamps (`timestamp`)**
  - **Method**: All timestamps are converted to UTC and formatted in ISO 8601 (`YYYY-MM-DDTHH:MM:SSZ`).
  - **Reason**: Ensures consistency and avoids timezone-related ambiguity.

## 2. Labeling Heuristics

The dataset is automatically labeled with `is_bruteforce_candidate` and `is_anomalous` flags based on a set of predefined rules. These labels are not perfect but serve as a strong baseline for the machine learning model.

### `is_bruteforce_candidate = 1`
This label is applied when an activity pattern strongly suggests a brute-force or credential stuffing attack. The conditions are:

- **High attempt count for a single username**: `attempt_count_for_username >= 10` within a 10-minute window.
- **High attempt count from a single IP**: `attempt_count_from_ip >= 50` across multiple usernames within a 10-minute window.
- **Distributed attack on a single username**: A large number of distinct IPs are used to target the same username in a short period.

### `is_anomalous = 1`
This is a broader label for suspicious activities that may not be brute-force but are still unusual.

- **Impossible Travel**: A successful login occurs from a new country or distant geographic location within minutes of a previous login.
- **Session Reuse**: A `session_id` is reused from a different IP address or user agent than the one it was created for.
- **Rate Limiting**: An IP address or username repeatedly triggers the `HTTP 429 Too Many Requests` status code.
- **Anomalous Success**: A successful login follows an unusually high number of failed attempts for that username.

## 4. Limitations & Notes

- **Label Accuracy**: The automated labels are based on heuristics and may contain false positives or false negatives. The ML model is intended to learn more nuanced patterns beyond these simple rules.
- **Simulated Data**: The initial dataset is generated from a simulated environment using `auth_scanner.py`. While based on realistic scenarios, it may not capture the full complexity of real-world user behavior.
- **Manual Review**: Some events may be flagged with a `notes` entry indicating they are candidates for manual review, especially in cases where the automated labeling is ambiguous.
